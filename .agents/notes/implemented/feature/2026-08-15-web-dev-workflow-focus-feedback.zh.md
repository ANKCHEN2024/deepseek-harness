# Agent Note: Web 工作流工具箱焦点与反馈打磨

Status: implemented

[English](2026-08-15-web-dev-workflow-focus-feedback.md) | 中文

## Problem

工具箱在动作反馈与焦点流转上有四类可用性缺口。其一，发送确认条固定在面板顶部挂载，与点击了哪个动作无关：在较长的详情列底部点击交付阶段动作时，确认条出现在视野之外，点击看起来像没有反应。其二，瞬时反馈（已发送、收藏已满）渲染在面板最末尾、所有阶段分组之下，在顶部操作的用户根本看不到。其三，焦点在发送的两端都会丢失：发送成功后挂载中的确认按钮随确认条卸载，焦点掉到 document body；发送进行中 Escape 又能关掉确认条，留下一个不可见的 busy 状态，直到请求结束前禁用所有按钮。其四，若干小反馈缺口：在任务范围输入框里按 Ctrl/Cmd+K 会在输入中途抢走焦点；搜索时阶段标题仍然可点击（且点击无效）；搜索框没有一致的清空入口与匹配反馈；执行模式块占两行浪费约 20px；带边框的收藏按钮让每个动作行的视觉元素翻倍。

## Decision

- 发送确认条挂 ref；既有的聚焦 effect 同时调用 `scrollIntoView({ block: 'nearest' })`（可选调用守卫，因为 jsdom 没有该方法），从任意滚动位置打开都能最小幅度地把确认条带入视野。
- 「已发送」与「收藏已满」反馈移到面板末尾的 `position: sticky; bottom` 气泡栈：面板滚动期间浮在可见底边，随面板末尾滚走，并自动消失（已发送 4 秒、收藏已满 3 秒）。
- 焦点流转：基于已发送状态的 `useLayoutEffect` 在发送后的 commit 之后把焦点还给触发的动作按钮；当该按钮已卸载（`recordRecent` 改变建议列表导致建议轮换）时，焦点落到面板根节点（`tabIndex={-1}`）而不是 body。发送条的 Escape 处理器始终 `preventDefault`，并在 `busy` 时忽略该键，因此进行中的发送无法被视觉上关闭。
- 搜索打磨：面板 keydown 在事件目标为任意输入框时跳过 `/` 与 Ctrl/Cmd+K（Escape 仍可从搜索框清空搜索）；自定义框内清空按钮（同时屏蔽 WebKit 原生取消按钮）清空并重新聚焦；一条 `role=status` 行报告匹配数量；搜索自动展开所有阶段，因此搜索期间阶段标题 `disabled`。
- 密度：执行模式块合并为单行（标签在左，双按钮分段控件在右）；收藏按钮改为无边框淡出样式，hover / focus-visible 时显现，与标题栏入口一致。

## Alternatives considered

### 为什么不把发送确认条渲染在被点击动作旁边？

在分组网格里锚定确认条需要逐行状态并重排两列网格，而且确认条的高度会挤开邻近动作。滚入视野保留顶部唯一稳定的确认条，动作幅度最小。

### 为什么不用 portal 式 toast？

槽位系统没有 toast 宿主；在详情列里做 fixed 定位浮层需要视口计算与主题协调，相比在既有滚动容器里用 `position: sticky` 收益很小。

### 为什么不在 Escape 时隐藏确认条而让发送继续？

在发送进行中隐藏确认条会让用户面对全部禁用且无可见原因的按钮；屏蔽按键让进行中状态保持诚实。

## Consequences

- 面板根节点成为程序化焦点目标（`tabIndex={-1}`）；测试断言焦点落在触发按钮或面板两者之一。
- `search.matches` 使用 `{n}` 占位符在渲染时替换——locale 系统没有插值。
- 搜索容器从隐式 `<label>` 改为带标签的 div（`htmlFor` + id），避免清空按钮嵌套在 label 里。
- 焦点与关闭规则延伸了[键盘与无障碍 note](2026-08-15-web-dev-workflow-keyboard-a11y.md)：发送条内的 Escape 现在是 busy 感知的空操作，搜索快捷键不再从输入框内触发。
