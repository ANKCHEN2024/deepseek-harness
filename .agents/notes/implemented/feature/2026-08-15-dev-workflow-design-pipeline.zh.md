# Agent Note: 开发流程工具箱设计流水线

Status: implemented

[English](2026-08-15-dev-workflow-design-pipeline.md) | 中文

## Problem

[Web 项目开发流程工具箱](2026-08-15-web-dev-workflow-toolbox.md)最初发布的四十八个动作把设计当作实现前的一个产出文字的步骤：`dev-ui-design` 明确只产出文字方案、不消费设计稿；没有任何动作把实现后的界面与设计对比；需求 → 用户故事 → 任务拆分 → 实现各阶段各自输出自由文本，下一个环节没有可读取的工件。设计意图从未成为可核对的约束，于是视觉走样、token 无人管理、无障碍只做静态检查。

## Decision

`@deepseek-ai/dsh-skill-dev-workflow` 与 `@deepseek-ai/dsh-client-ui-dev-workflow` 围绕两个机制新增一个动作、加深六个既有动作。

**设计稿消费与视觉核对。** `dev-ui-design` 现在先消费设计稿（用环境中的读图工具读取截图、Figma 导出、线框图等图片），提取布局、间距、配色、字体、组件与状态，标注设计稿未交代的内容，并给出每个视图的验收条件。质量组新增 `dev-visual-check` 动作：环境提供浏览器 / 截图工具时直接截取实现画面（没有时明确告诉用户需要截哪些页面与状态），再逐视图、逐状态对照设计规范，输出按阻断 / 主要 / 次要排序的偏差清单，只核对不修代码。`dev-a11y-check` 改为运行时优先：有浏览器工具时实际打开目标页面检查，否则退化为静态检查。`dev-component-library` 增加设计 token 提取（语义名、原始值、代码位置）。

**阶段间工件交接。** 流水线各阶段共享 `docs/` 下的固定工件：`requirements.md`、`user-stories.md`、`task-breakdown.md`、`ui-design.md`、`visual-check.md`。每个阶段在工件存在时先读取上游工件，且仅在可改代码模式下写入自己的工件（只分析模式输出同样的分节正文）。`dev-task-breakdown` 还会在环境提供 todo 工具时把任务列表镜像进 todo 并保持一致；`dev-implement` 会读取流水线工件，让改动对齐其范围与验收标准。

随包 skill 正文（`catalog.ts`）与客户端回退提示词（`prompts.ts`）同步携带新措辞；动作目录、风险表（`visual-check` 为 `writes-repo`，因为可改代码模式会写报告文件）、分组布局与中英文 locale 条目同步更新。工具箱动作数现为四十九个。

## Alternatives considered

### 为什么不做设计资产能力包？

截图、图像生成与视觉 diff 引擎是运行时能力，dev-workflow skill 目录刻意保持独立。skill 消费环境提供的读图与浏览器工具，缺失时改为明确指示用户，与既有的「工具可用时使用」约定一致。以后可单独补能力 seam，无需改动 skill 措辞。

### 为什么不新增「设计核对」阶段组？

工具箱已有设计阶段；视觉核对是验证动作，放在质量组无障碍检查旁边，保持阶段语义（设计 = 产出，质量 = 验证）不变。

### 为什么工件放在 `docs/` 而不是专用计划目录？

`docs/` 是仓库标准的项目文档位置，流水线工件就是普通项目文档。专用目录需要一条没有消费者的新约定。

## Consequences

- 设计意图成为可核对输入：设计稿进入 `ui-design`，`visual-check` 按规范核对实现，补上视觉走样缺口。
- 工件链让连续的工具箱动作可以组合：每个阶段读取上游工件，而不是从会话里重新推导范围。
- Skill 正文与回退提示词仍是两个包里的纯文本，且与环境解耦（浏览器 / 读图工具都是可选的），新动作缺失工具时退化为明确的用户指示，而不是失败。
- 客户端搜索与设计相关的匹配数从两个变为三个（视觉核对的说明含「设计」）；面板测试固定了这个新数字。
